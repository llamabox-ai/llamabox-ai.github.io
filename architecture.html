How LlamaBox works — and why

LlamaBox runs large language models entirely on your Android phone, with no cloud and no accounts. Here is the architecture behind that, and the reasoning behind each decision.

Read the full architecture doc on GitHub →

1.What LlamaBox is

A React Native Android app that runs LLMs on-device using llama.cpp via the llama.rn bridge. You download a quantized GGUF model, the app memory-maps it into RAM, and tokens are generated on your phone's CPU. No inference call ever leaves the device.

  • Platform: Android 7.0+ (arm64). iOS is a future target.
  • Framework: React Native 0.81, New Architecture (JSI/TurboModules)
  • Inference: llama.rn 0.12.0-rc.8 wrapping llama.cpp
  • Compute today: CPU-only (4 threads, ARM NEON)
  • State: Zustand (UI) · SQLite (history) · AsyncStorage (settings)

2.High-level architecture

JavaScript layer   →   React Native bridge (JSI)   →   Native (C++)
  UI + Zustand                                    llama.rn → llama.cpp → ggml (CPU)

Three layers: a TypeScript UI and state layer, a JSI bridge with near-zero overhead (critical for the hot token-streaming path), and a native C++ inference core.

3.The decisions, explained

On-device / offline

Privacy is the product. The moment inference touches a server, the privacy claim becomes unverifiable. Running locally makes the claim auditable — there is genuinely no code path that sends your prompts anywhere. Offline is a consequence of privacy, not just a feature.

llama.cpp + llama.rn

llama.cpp is the most mature, mobile-optimized CPU engine for GGUF, with hand-tuned ARM NEON kernels. llama.rn is its React Native bridge. We get native-class inference without writing our own JNI.

React Native + New Architecture

One TypeScript codebase runs on Android today and can target iOS later. The New Architecture (JSI) matters specifically here: inference calls pass large token buffers between JS and native, and JSI avoids the legacy async bridge's serialization cost.

CPU-only today (GPU is planned)

On every device tested, GPU detection returns none. The current build uses llama.rn's prebuilt binaries, whose Java loader only attempts the OpenCL-capable library when a Hexagon DSP is also detected — coupling two independent backends. The roadmap: a GPU diagnostics panel, decoupling OpenCL from Hexagon, and an Auto/CPU/GPU selector with a per-device smoke test. Until that is validated, CPU-only is the honest default.

Vision encoder forced to CPU

Vision encoding is a one-shot burst that saturates GPU memory. On Android, running the CLIP-style encoder on the GPU can freeze the system UI for seconds. Forcing use_gpu: false for the encoder — while the text decoder can still use GPU layers — keeps the interface responsive. The encoder runs once per image; the decoder runs continuously.

No Reanimated

Reanimated crashes with the New Architecture in this setup. Every animation uses RN's built-in Animated API with useNativeDriver: true. New animation code must follow this or the app crashes.

Three stores (Zustand / SQLite / AsyncStorage)

Each does what it is best at: Zustand for reactive in-memory UI state, SQLite (WAL) for durable chat history, AsyncStorage for key/value settings. Keeping them separate is simpler and faster than fighting one store's limits.

Memory-mapped weights, no mlock

A 1–4 GB GGUF is mmap'd and paged in on demand — fast startup, low apparent RAM. We do not pin pages in RAM (mlock) because on low-memory phones that risks OOM. Tradeoff: occasional micro-stutters from page faults.

KV cache is not persisted

Resuming an old chat replays the whole history and rebuilds the KV cache from scratch, so long chats are slower to first token. Persisting a multi-hundred-MB FP16 cache across model/context changes is fragile and unsafe. We chose simple-and-correct over fast-and-fragile — a known limitation, not a bug.

Context 2048 (4096 for vision)

KV cache grows linearly with context. 2048 is the sweet spot for fluid chat on mid-range phones. Vision auto-bumps to 4096 (image tokens are expensive, 1000+ each) and disables context shifting, which can corrupt image-embedding KV entries.

Q4_K_M quantization

Best speed/quality tradeoff on CPU. Smaller degrades quality noticeably; larger is slower with marginal gains on a phone. Qwen2.5 0.5B and SmolLM2 360M run smoothly even on mid-range devices.

AGPL-3.0 + reserved trademark

A closed-source privacy app asks you to trust its claim; open source lets you verify it. AGPL-3.0 (strong copyleft) means any fork that ships must also be open — blocking silent closed clones. "LlamaBox" is a reserved trademark so the name cannot endorse derived works. A commercial license is available for closed-source commercial use.

4.Inference, in brief

Per output token: embedding lookup → transformer block × N layers across 4 worker threads (LayerNorm, Q/K/V GEMM, RoPE, attention, FFN) → final projection → sampling → KV-cache append. On a mid-range device with a ~1B Q4_K_M model, generation is roughly 2–8 tokens/sec; prompt processing 1–5 tok/s; model load 5–30 s.

5.Multimodal vision

Images are picked via expo-image-picker, copied to persistent storage (the picker's temp URIs are unreliable), and sent as an OpenAI-style content array with a file:// image. A model is vision-capable when its filename matches vision keywords and a sibling mmproj file is found.

6.State & persistence

Two Zustand stores (chatStore, modelStore) drive the UI. SQLite stores conversations and messages (with an attachments column for image metadata, migrated idempotently). AsyncStorage holds settings and per-model overrides. Sending a message: build the prompt, prune to fit context (system prompt always kept), insert the user message + a streaming placeholder, stream tokens back on a ~150 ms throttled UI tick, then finalize in SQLite.

8.Limitations & roadmap

  • Today: CPU-only; KV cache not persisted; one model at a time; Android-first.
  • Planned: GPU (OpenCL) enablement with diagnostics + engine selector; expanded model presets; plugin/tool-use system; more vision preset packs; auto context sizing; iOS port.
